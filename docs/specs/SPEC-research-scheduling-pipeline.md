## What actually shipped (differs from the original design below)

### #61 — Mon 09:15 sync job — ✅ shipped, different implementation

Original design proposed a **new** plist `com.data-wise.research-sync-board.plist`. What shipped
instead: extended the **existing** `com.data-wise.atlas-sync.plist` with a new wrapper script
`scripts/sync-research-board.sh` (runs `atlas sync --research`, `atlas sync -p
~/projects/r-packages/active`, then `obs research board --out <vault>/.../_RESEARCH-BOARD.md`),
same 09:15 slot in the chain. Closure comment reports a verified run: 15 research projects synced,
board rendered. No new plist file exists on disk — that's expected, not a gap.

### #62 — dedupe mediationverse-status-sync — ✅ shipped, opposite decision from the spec

Original design said: **retire the launchd job, keep the cloud task** (rationale: cloud task more
reliable, doesn't need the Mac awake at a specific time). What actually shipped: **the reverse** —
kept the launchd job, disabled the cloud task instead (rationale per closure comment: launchd is
deterministic, local, no Claude-session dependency). This was a deliberate call, not an oversight.

### #63 — retire mediationverse-status-sync.py — still open, correctly gated

Untouched, per design — gated on #61/#62 landing and one verified live run. #61/#62 have landed;
the live run has not been confirmed (see Unresolved below).

## Unresolved — found during 2026-07-15 adverse review, not previously tracked

`launchctl print gui/$(id -u)/com.data-wise.mediationverse-status-sync` currently shows
**`last exit code = 1`** — i.e. the job #62 chose to keep is showing a failure state right now.

Investigation so far (read-only, no changes made):
- Manual `python3 mediationverse-status-sync.py --dry-run` runs clean (exit 0, valid table output).
  The script is pure file I/O — no subprocess/PATH-dependent calls — so launchd's minimal
  environment isn't an obvious suspect.
- **No log file exists** at `~/Library/Logs/mediationverse-status-sync.log`, despite the plist
  pointing both stdout and stderr there. Either the job has never actually fired since #62 was
  decided (macOS silently skips a `StartCalendarInterval` job if the Mac is asleep at the
  scheduled time — a known behavior, not a bug), or a log rotation/cleanup removed prior evidence.
- Plist itself unchanged since `Jun 20 01:54:27 2026` — no edits happened as part of the #62 fix,
  consistent with "kept as-is."

**Can't distinguish from static inspection**: (a) stale exit-1 from before #62 landed, job is
actually fine now, vs. (b) job is still genuinely broken and has silently failed every Monday since.
At least 4 Mondays (6/22, 6/29, 7/6, 7/13) have passed without this being confirmed either way —
the original spec's own "verify next Monday run" step for #63 appears to have never closed out.

**Before touching anything**: this needs an *observed* Monday-morning run (watch `launchctl list`
immediately after 09:00 next Monday, or add temporary logging) — not another round of static
inspection, which has already hit its limit here.
